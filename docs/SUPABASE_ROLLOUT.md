# 기존 Supabase 보존과 인증 이전

기존 데이터베이스의 연결과 전체 마이그레이션 이력은 아직 확인할 수 없습니다. **검증용 새 스키마가 기존 운영 스키마와 같다고 가정하지 않습니다.** CI는 매번 폐기하는 로컬 Supabase/PostgreSQL만 사용합니다.

## 읽기 전용 조사

소유자가 계정을 연결하면 담당 에이전트가 프로젝트를 확인하고 `ops/supabase-audit.sql`의 조회를 수행합니다. 관련 12개 테이블의 열·타입·기본값·관계, RLS·정책, 함수·실행 권한과 Realtime 등록을 확인합니다. Auth 익명 가입·요청 제한, 백업 상태, 배포 환경 변수 이름도 확인합니다. 사용자 내용·키·토큰은 공개 저장소나 작업 로그에 남기지 않습니다.

## 백업과 복구

1. DB 스키마·데이터·정책·함수·역할과 Auth 연결 정보를 암호화한 소유자 관리 저장소에 보존합니다. 키는 별도 보관하고 민감한 Auth 백업을 CI 아티팩트에 올리지 않습니다.
2. 해시·시각·행 수·관계·소유권을 기록하고 격리 프로젝트에서 실제 복원합니다. Storage 사용 시 DB와 별도로 객체 파일도 보존합니다.
3. 복원 뒤 접근 거부·방장 권한·종료 상태·메시지·공지·일정 보존을 검사하고 복구 시간을 측정합니다. 백업 존재만으로 운영 변경을 시작하지 않습니다.

## 신원과 데이터 보존

브라우저의 임의 UUID는 인증된 소유권 증거가 아닙니다. `wyd_sender_id` 제출만으로 방장을 복구하는 API를 만들지 않습니다. 기존 행/ID를 삭제하거나 강제로 Auth UUID로 바꾸지 않습니다. 새 참가자는 Supabase Anonymous Auth로 가입 화면 없이 참여하고, 서버는 검증된 JWT의 `auth.uid()`와 멤버십으로 방장·운영자·참가자 권한을 결정합니다.

기존 방장은 소유자의 별도 확인과 관리된 매핑으로 연결해야 합니다. 실제 소유 확인 증거와 익명 세션 분실 복구 방법은 프로젝트 조사 후 확정합니다. UI가 `wyd_security_version()` 1을 확인하는 것은 오접속 방지이며, 보안 경계는 RLS/RPC입니다. 기존 공개 정책이 남으면 구버전 앱으로 접근할 수 있으므로 전체 정책을 점검합니다.

## 전환과 복구 계획

`202609090001_verified_identity.sql`은 `events`가 있으면 중단하는 새 검증 환경용입니다. `202609090002_translation_budget.sql`은 비공개 사용량 예약을 추가합니다. **기존 프로젝트에 그대로 db push하지 않습니다.** 실제 열 타입과 관계를 조사한 뒤 별도 보존 마이그레이션을 작성합니다.

새 열/정책 준비 → 신원 매핑 → 백필·읽기 비교 → 점검 시간 내 구버전 쓰기 차단 → RLS/RPC 전환 → 새 UI 배포를 구체화합니다. 운영 데이터·보안 변경은 복구 증거와 SQL을 제시한 뒤 소유자 승인을 받습니다. 실패하면 쓰기를 중지하고 검증된 백업으로 복구하며, 안전하지 않은 옛 권한을 임의로 다시 열지 않습니다.

실제 두 기기로 QR 참가·언어·긴급 원문/번역/실패 상태·중복·끊김/복귀·읽음/확인·일정·권한 거부·종료를 확인합니다. 대규모 참가/전송과 종료 경합은 별도 검사합니다. 현재 3인 CI는 부하 테스트가 아닙니다.

근거: [Anonymous Auth](https://supabase.com/docs/guides/auth/auth-anonymous), [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [Realtime 준비와 복구](https://supabase.com/docs/guides/troubleshooting/realtime-postgres-changes-troubleshooting).
